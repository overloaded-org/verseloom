# DEV-only 候选来源诊断

这是v0.3先导实验之后提出的开发诊断。四种策略及计数规则先写入freeze.json，再计算训练候选与开发集覆盖。没有回改先导候选、训练或测试结果，也没有读取模型或预测文件。

## 范围

候选仅从2502首训练诗建立，按五言、七言分别统计，保持原字形，不跨行拼接。目标为547首开发诗的四个下句首二字，共2188题、508族。原task文件没有打开；脚本从poems.jsonl筛出train/dev记录，在JSON解码前跳过test记录。原始混合分割文件整体SHA会读取文件字节，但不会解析被跳过的测试诗或生成测试任务。

“合计”是五言池数加七言池数，同一文本若存在两个池中会计两次；跨句长去重的不同片段总数也单独保存在report.json，分别为1375、7231、5239、11066。

诗族等权覆盖先对一个族内所有开发题求覆盖比例，再对508族等权平均。该指标不是准确率；一首诗或一个族中的多个题不被错误当成独立诗族。

## 可以据此作的开发判断

候选来源和最低频次显著限制原文复原的词表上限；只降低首部片段的最低频次，也会扩大覆盖。扩大到训练全行相邻片段有更高开发覆盖，同时候选量增加，需要后续独立检索与评分成本检验。七言训练语料和候选相对稀少，在四种策略下都存在明显覆盖限制。

这些数字不测量top16检索召回，不表示模型已经能够从词表中选中原文，更不是文学质量或测试集改善。策略③④包含固定相邻字片段，不声称每个片段都是词法上的词。四种策略全部报告，不隐去覆盖较低的方案。

## 可复算证据

- freeze.json：计算前配置、来源SHA、脚本SHA和冻结时间。
- candidate_counts.json：四种训练候选表及其原始频次。
- dev_coverage.jsonl：每个开发任务的来源身份、观测前缀和四策略是否覆盖。
- report.json：完整结果、句长切片、族等权口径与限制。
- manifest.json：全部派生输出SHA。
